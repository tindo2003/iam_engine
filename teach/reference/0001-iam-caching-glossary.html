IAM Evaluation Caching — Glossary

Compressed reference for Lesson 0001 and onward. Designed to be re-read, not re-derived — print this one.

Decision cache

A cache keyed by (principal, action, resource) (sometimes also the policy version) mapping to the boolean evaluation result. The entire point of caching in an IAM system: skip re-walking policy statements for a repeat request.

New enemy problem

Zanzibar's name for a cached Allow surviving a real revoke, so a principal who should have just lost access keeps acting with it until the cache catches up. The defining failure mode any IAM caching design has to rule out, not just make rare.

Invalidation strategies

TTL-based
Cache entries expire after a fixed time window. Correction from lesson 0001: this isn't a fallback for lazy systems — it's what SpiceDB (real, production Zanzibar) actually uses by default, a flat 5-second window. See Lesson 0002.
Version-stamped
Every write bumps a monotonic version/timestamp; a cached decision carries the version it was computed against. SpiceDB's twist: it quantizes the timestamp into fixed buckets (e.g. 1-second windows) so many real requests collide onto the same cache key — the quantization is what makes the cache useful, not just correct.
Revision floor (lesson 0007)
Derive the snapshot from when the policy data was last WRITTEN, not from the clock: max(<consistency choice>, graph.revision()). A write instantly pushes every later request onto a new key, so pre-write entries become unreachable rather than merely expiring. This is the new enemy problem solved rather than bounded, and it must apply to every consistency level -- confining it to at_least_as_fresh would leave ordinary traffic reading stale answers. Sharing survives: between the write and the next bucket boundary, every request converges on the revision itself.
Event-driven / opt-in strong consistency
Rather than push every write into every cache, SpiceDB pushes the choice to the caller: a request can ask for fully_consistent (bypass the cache entirely) or at_least_as_fresh (use a ZedToken to guarantee a snapshot at least that recent, while still allowing cache reuse). Strong consistency is opt-in per request, not automatic.

TrueTime / commit wait

How Spanner (and therefore Zanzibar) makes a revision trustworthy across machines. TT.now() returns an interval [earliest, latest] rather than a point, kept narrow (ε under ~4ms) by GPS plus atomic clocks. On commit, Spanner waits until the chosen timestamp is certainly in the past everywhere (~8ms) before making the write visible — after which no later transaction anywhere can claim an earlier timestamp, with zero coordination between writers.

Why nothing cheaper works: the new enemy problem needs real-time ordering, not causal ordering. Logical clocks (Lamport, vector) only order events that communicated — a revoke in one datacenter and a read in another never did, so they report "concurrent", which is exactly the answer that lets a stale Allow through. Without atomic clocks you approximate: CockroachDB uses hybrid logical clocks plus a configured max-offset assumption, weaker and degrading if NTP drifts past the bound.

Allow/Deny caching asymmetry

Caching an Allow is the riskier of the two: a stale Allow is an active security hole. A stale Deny just means a legitimate user has to retry — annoying, not dangerous. Some systems deliberately cache denies longer or more aggressively than allows for exactly this reason.

Singleflight (request coalescing)

Running a missing key's computation at most once across all threads asking for it: the first caller registers an in-flight entry and computes, later arrivals wait on its result. Distinct from thread safety, and the distinction is the point — a mutex protects the container, so N concurrent misses still run N full evaluations and store N identical answers. Correct, and N times the work.

Three details that are load-bearing rather than decorative: compute runs with no lock held (else a slow evaluation blocks every unrelated reader); registration takes an exclusive lock and re-checks the cache under it (under a shared lock two threads could both find no flight and both register one); and a throwing compute must retire its flight before rethrowing, or every waiter blocks forever on a promise nobody will fulfil.

Deduplicates within one process only. Ten processes behind a load balancer still compute a key ten times — that is what consistent hashing addresses.

shared_mutex vs mutex

Authorization data is read constantly and written rarely, so readers should not queue behind each other. shared_lock for reads, unique_lock for writes. One caveat worth internalising: a multi-step read (a graph traversal) needs one lock across the whole walk, not one per lookup — otherwise a write lands mid-traversal and the result mixes pre- and post-write state, describing a world that never existed.

Verifying concurrency work

Passing tests are weak evidence; a race can hide for a thousand runs. Build under ThreadSanitizer. Then validate the sanitizer itself against a deliberately racy program — an uninstrumented TSan and a genuinely clean one both report nothing, and they look identical. Evidence of absence is only evidence if the detector works.

Policy indexing

Scanning every statement on every request (what iam-engine's current PolicyEngine::evaluate does) doesn't scale. Real engines build an index at policy-load time — a trie/prefix-tree keyed by action and resource — so a lookup narrows to a handful of candidate statements. Zanzibar's "Leopard" indexing system is this idea at Google's scale.

Bitmask actions

Map each known action string to a bit position once, at load time. db:read | db:write becomes a single integer; matching becomes a bitwise & instead of a string comparison — directly applicable to Statement::matchesAction in iam-engine.

PEP / PDP / PIP / PAP

(NIST SP 800-162's ABAC architecture — not caching-specific, but the frame every caching decision sits inside.)

PEP — Policy Enforcement Point
Intercepts the request, asks the PDP for a decision, enforces it.
PDP — Policy Decision Point
The actual evaluation engine. This is what PolicyEngine is, and what a decision cache sits in front of.
PIP — Policy Information Point
Supplies attributes the PDP needs but doesn't already have (e.g. a user's department, current time).
PAP — Policy Administration Point
Where policies are authored, tested, and stored. A write here is what a cache needs to notice.
