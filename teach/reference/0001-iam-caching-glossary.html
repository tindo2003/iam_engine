IAM Evaluation Caching — Glossary

Compressed reference for Lesson 0001 and onward. Designed to be re-read, not re-derived — print this one.

Decision cache

A cache keyed by (principal, action, resource) (sometimes also the policy version) mapping to the boolean evaluation result. The entire point of caching in an IAM system: skip re-walking policy statements for a repeat request.

New enemy problem

Zanzibar's name for a cached Allow surviving a real revoke, so a principal who should have just lost access keeps acting with it until the cache catches up. The defining failure mode any IAM caching design has to rule out, not just make rare.

Invalidation strategies

TTL-based
Cache entries expire after a fixed time window. Simple, but the size of your new-enemy exposure equals the TTL. Most systems that ship "good enough" caching use this.
Version-stamped
Every policy write bumps a monotonic version counter (or, in Zanzibar, a "zookie" consistency token tied to a snapshot). A cached decision carries the version it was computed against; any write invalidates every entry at once by making the version stale, instead of hunting down individual keys.
Event-driven
A policy change publishes an explicit invalidation event (pub/sub) to every cache holder. Fastest real revocation, most infrastructure to build and run correctly.

Allow/Deny caching asymmetry

Caching an Allow is the riskier of the two: a stale Allow is an active security hole. A stale Deny just means a legitimate user has to retry — annoying, not dangerous. Some systems deliberately cache denies longer or more aggressively than allows for exactly this reason.

Policy indexing

Scanning every statement on every request (what iam-engine's current PolicyEngine::evaluate does) doesn't scale. Real engines build an index at policy-load time — a trie/prefix-tree keyed by action and resource — so a lookup narrows to a handful of candidate statements. Zanzibar's "Leopard" indexing system is this idea at Google's scale.

Bitmask actions

Map each known action string to a bit position once, at load time. db:read | db:write becomes a single integer; matching becomes a bitwise & instead of a string comparison — directly applicable to Statement::matchesAction in iam-engine.

PEP / PDP / PIP / PAP

(NIST SP 800-162's ABAC architecture — not caching-specific, but the frame every caching decision sits inside.)

PEP — Policy Enforcement Point
Intercepts the request, asks the PDP for a decision, enforces it.
PDP — Policy Decision Point
The actual evaluation engine. This is what PolicyEngine is, and what a decision cache sits in front of.
PIP — Policy Information Point
Supplies attributes the PDP needs but doesn't already have (e.g. a user's department, current time).
PAP — Policy Administration Point
Where policies are authored, tested, and stored. A write here is what a cache needs to notice.
