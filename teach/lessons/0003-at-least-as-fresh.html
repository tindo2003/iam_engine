At Least As Fresh: A Causal Token for iam-engine

Follows Lesson 0002, which built the two extremes — MinimizeLatency (cache-friendly, bounded staleness) and FullyConsistent (bypass entirely) — and explicitly left the middle ground as "a further exercise." This is that exercise.

The gap between the two extremes

MinimizeLatency is fast but can return a stale answer. FullyConsistent is always correct but throws the cache away — every single request pays the full evaluation cost, even ones that don't actually need that guarantee. Most real checks need something in between: "I don't need the absolute latest state, but I do need at least what I already know happened."

What a ZedToken actually is

From lesson 0001: a zookie/ZedToken is an opaque token handed back after a write, encoding a point in the system's causal timeline. at_least_as_fresh takes one of these tokens on a later check and guarantees the result reflects a snapshot at or after that point — never before it — while still allowing cache reuse for anything that already qualifies. It's the mechanism that makes external consistency a real, callable thing instead of a paper concept.

Modeling it in iam-engine

You don't have a real distributed transaction log, so you don't need anything as elaborate as SpiceDB's. A single monotonically increasing counter is enough to model the same idea:

  • A PolicyVersion (just a uint64_t) that increments whenever the caller knows policies changed — this stands in for "the token returned by a write."
  • Every cache Entry also records the version it was computed against, alongside its timestamp.
  • at_least_as_fresh(minVersion) semantics: a cache hit requires both "still within TTL" and "entry.version >= minVersion." An entry that's time-fresh but version-stale is still a miss — the version floor is a harder requirement than the TTL, not an alternative to it.

This is deliberately a stripped-down stand-in, not a faithful ZedToken — real Zanzibar tokens encode a globally meaningful transaction position; yours only needs to mean something within one DecisionCache instance. That's fine. The point of this exercise is the consistency semantics, not reproducing Zanzibar's exact wire format.

Check your understanding

A client just revoked a permission and wants any of their own later checks to reflect that — but doesn't need every unrelated request in the system to also skip the cache. Which consistency level fits?

A cache entry is 1 second old under a 60-second TTL (still clearly fresh by time), but its stored version is 3, and the caller requests at_least_as_fresh(minVersion=5). What happens?

Build it into iam-engine

Rescoped, concrete steps for your own checkout — no full code this time, you know the pattern by now from lesson 0002:

  1. Add a using PolicyVersion = std::uint64_t; (in cache.hpp is fine).
  2. Add a version field to Entry, and a currentVersion parameter to put() — every call to put needs to know what version it's storing against.
  3. Add an overload (or optional parameter) to get() that takes an optional PolicyVersion minVersion. When provided, a hit requires entry.version >= minVersion in addition to the existing TTL check. When absent, behave exactly as today (that's what MinimizeLatency keeps using).
  4. Add Consistency::AtLeastAsFresh to the enum, and thread a PolicyVersion parameter through evaluateCached for that case.
  5. Write the test that actually matters: a cache entry stored at version 3, well within TTL, requested with minVersion = 5 — must be a miss (re-evaluates and re-caches at the new current version), even though the exact same request under plain MinimizeLatency would have been a hit.

Ask me before you start if the version-vs-TTL interaction (both must pass, neither alone is enough) isn't clicking yet — that's the one idea in this lesson worth being sure about before writing code.
