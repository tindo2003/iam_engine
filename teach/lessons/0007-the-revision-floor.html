The Revision Floor

Six lessons ago you learned to bound the new enemy problem. This one closes it. It is also where the PAP — the missing administration point — finally has something concrete to attach to.

What lesson 0001 actually settled for

Go back and reread the promise made in lesson 0001: a cached Allow must not survive a real revoke. Everything since has bounded that window — TTL first, then the quantization bucket — but never eliminated it. Revoke alice's access mid-bucket today and she keeps it until the boundary rolls over.

That is not a bug in the implementation. It is the honest consequence of where the snapshot comes from: 

snapshot = quantize(now, bucket)   // derived from the CLOCK

The snapshot is supposed to mean "which version of the policy data this answer was computed against." Deriving it from wall-clock time makes that a guess. It is a good guess when data changes rarely — but it has no way to know a write just happened.

The fix: let the data speak

Give RoleGraph a revision() — the moment it was last written to — and use it as a floor on whatever the consistency level would otherwise have chosen: 

snapshot = max(<per-consistency choice>, graph.revision())

Now a write at time R instantly pushes every subsequent request onto a key at or after R. The pre-write entries are not expired, not evicted, not invalidated — they are simply unreachable, because nobody will ever compute their key again. That is a stronger guarantee than expiry, and it costs nothing to enforce.

The trap: it must apply to every level

It is tempting to treat the revision as just another token and fold it into AtLeastAsFresh, which already takes a floor. That would be wrong in the most dangerous way possible: ordinary MinimizeLatency traffic — which is nearly all traffic — would keep reading pre-write entries for the rest of the bucket. The requests most likely to be exploiting a just-revoked permission are exactly the ones that would not be protected.

Why this does not wreck sharing

The obvious worry: if a write drags everyone onto an unquantized timestamp, does each request get its own private key? No — because they all get the same one. Write at t=1500, bucket 1000: 

request at   quantize(now)   revision   snapshot   shared?
   1600          1000          1500       1500     yes -- with all others
   1900          1000          1500       1500     same entry
   2100          2000          1500       2000     back on the bucket

Between the write and the next boundary, everyone converges on R itself. After it, everyone moves back onto the bucket together. The cache is never fragmented; it just briefly rallies around a different shared value.

Where the PAP fits

This is the gap flagged back in roles.hpp: nothing tied a cached answer to the data version that produced it. Real Zanzibar gets this for free — Spanner assigns every write a TrueTime timestamp, so a revision is a fact about the database, not an assertion by a caller.

revision() is that mechanism in miniature. It is still not a PAP: nothing here persists a write, authorises who may make it, or audits it afterwards. But it is the hook a PAP would drive, and building one no longer requires touching the decision path at all.

Check your understanding

Why must the revision floor apply to MinimizeLatency, not only to AtLeastAsFresh?

A write lands at t=1500 with a 1000ms bucket. Requests arrive at 1600 and 1900. What snapshot does each select?

Build it into iam-engine

The scaffold is committed; three TODOs, and 4 tests currently red:

  1. RoleGraph::addRole — stamp revision_ with clock_().
  2. RoleGraph::assign — the same. Both are writes; miss either one and a cached answer outlives the change that should have killed it.
  3. PolicyEngine::selectSnapshot — apply std::max(chosen, revision) uniformly. The switch currently returns straight out of each case, so restructure it to compute into a local first — otherwise it is far too easy to apply the floor to two levels and quietly forget the third.
ctest --test-dir build -R "SelectSnapshot|AWriteInvalidates" --output-on-failure

The one to watch is RbacCached.AWriteInvalidatesImmediatelyNotAtTheBucketBoundary. Alice is allowed and cached; mid-bucket she is assigned a suspended role that denies. Without the floor she keeps the access she has just lost. That test is lesson 0001's scenario, run against real code, six lessons later.

Worth being sure about before you start: why the floor is max() rather than replacing the chosen snapshot outright. If that is not obvious, ask — it is the difference between preserving sharing and destroying it.
