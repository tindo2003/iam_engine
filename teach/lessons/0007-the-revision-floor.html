The Revision Floor

Six lessons ago you learned to bound the new enemy problem. This one closes it. It is also where the PAP — the missing administration point — finally has something concrete to attach to.

What lesson 0001 actually settled for

Go back and reread the promise made in lesson 0001: a cached Allow must not survive a real revoke. Everything since has bounded that window — TTL first, then the quantization bucket — but never eliminated it. Revoke alice's access mid-bucket today and she keeps it until the boundary rolls over.

That is not a bug in the implementation. It is the honest consequence of where the snapshot comes from: 

snapshot = quantize(now, bucket)   // derived from the CLOCK

The snapshot is supposed to mean "which version of the policy data this answer was computed against." Deriving it from wall-clock time makes that a guess. It is a good guess when data changes rarely — but it has no way to know a write just happened.

The fix: let the data speak

Give RoleGraph a revision() — the moment it was last written to — and use it as a floor on whatever the consistency level would otherwise have chosen: 

snapshot = max(<per-consistency choice>, graph.revision())

Now a write at time R instantly pushes every subsequent request onto a key at or after R. The pre-write entries are not expired, not evicted, not invalidated — they are simply unreachable, because nobody will ever compute their key again. That is a stronger guarantee than expiry, and it costs nothing to enforce.

The trap: it must apply to every level

It is tempting to treat the revision as just another token and fold it into AtLeastAsFresh, which already takes a floor. That would be wrong in the most dangerous way possible: ordinary MinimizeLatency traffic — which is nearly all traffic — would keep reading pre-write entries for the rest of the bucket. The requests most likely to be exploiting a just-revoked permission are exactly the ones that would not be protected.

Who is doing the writing?

"A write" here means exactly one thing: somebody called addRole() or assign(). Conceptually that is the PAP's job — an admin console, an HR sync, a Terraform apply. Concretely there is no PAP in this project, so it is simply whoever holds a non-const RoleGraph&. In the test below, it is the test.

The read/write split is already drawn correctly, though: every PolicyEngine function takes const RoleGraph&, so the decision path structurally cannot write. Only a caller with a mutable reference can — and that caller is the PAP-shaped hole.

Two things a real PAP would add that this does not. Authorisation of the write itself: right now anyone with a mutable reference can hand alice any role. That is a genuinely recursive problem — "who may change policy" is an authorization question, which AWS answers by having IAM check iam:PutRolePolicy, so a real PAP calls back into the PDP to authorise its own operations. An authoritative clock: here revision_ = clock_() is stamped by the graph itself. In Zanzibar the write goes to Spanner and Spanner assigns the TrueTime timestamp — the revision is a fact the database asserts, globally ordered across every writer. The local version works for one in-process graph and falls apart the moment there are two writers on two machines.

revision vs. snapshot: two things of the same type

Both are a Snapshot, which is exactly what makes them easy to conflate. They answer different questions and belong to different things. 

                 revision                    snapshot
belongs to       the DATA (RoleGraph)        a REQUEST
means            "last written at"           "evaluating as of"
changes when     someone writes              clock advances, OR revision jumps
how many alive   exactly one, always moving  many at once, each frozen forever
owned by         RoleGraph                   computed per call, becomes cache key

The relationship is one-way

The revision is an input to computing a snapshot, never the reverse: 

RoleGraph.revision() --+
Consistency -----------+
minSnapshot (token) ---+--> selectSnapshot() --> snapshot --> cache key
now -------------------+
bucketSize ------------+

Nothing flows back. The cache never touches the graph; the graph does not know a cache exists. selectSnapshot() is the only place they meet, and it is a pure function over plain values — which is precisely why neither component has to know about the other.

The invariant it enforces: snapshot >= revision, always. An answer can never claim to describe a world older than the last write.

Watch both evolve

With a 1000ms bucket:

  t     event            revision   quantize(now)   snapshot   why
  ----  ---------------  ---------  --------------  ---------  ---------------------------
     0  graph created    epoch      0                       0  never written
   100  addRole            *100*    0                       -  write bumps revision
   150  alice checks       100      0                   *100*  floor wins; bucket pre-dates it
   900  bob checks         100      0                   *100*  same key -> shared with alice
  1100  alice checks       100      1000               *1000*  bucket overtook the revision
  1500  assign            *1500*    1000                    -  write bumps revision again
  1600  alice checks       1500     1000               *1500*  floor wins again
  2100  alice checks       1500     2000               *2000*  bucket overtakes again

The snapshot is max() of two rising quantities: one climbing in steps (the bucket) and one jumping on writes (the revision). Whichever is ahead wins. That sawtooth is the whole mechanism.

A write deletes nothing

At t=1600 the cache still physically holds entries at snapshots 0, 100 and 1000. They are not corrupt and not expired — they are perfectly valid answers about the world as it was at those moments. They are merely unreachable, because no future request will ever compute a snapshot below 1500 again.

That is the difference from invalidation. TTL-style invalidation says "this answer has gone bad." The revision floor says "that answer is still true about a world nobody is asking about anymore." Eviction (ttl) reclaims them eventually, but that is capacity housekeeping — entirely separate from correctness.

Why this does not wreck sharing

The obvious worry: if a write drags everyone onto an unquantized timestamp, does each request get its own private key? No — because they all get the same one. Take a write at t=1500 with a 1000ms bucket: 

request at   quantize(now)   revision   snapshot   shared?
   1600          1000          1500       1500     yes -- with all others
   1900          1000          1500       1500     same entry
   2100          2000          1500       2000     back on the bucket

Between the write and the next boundary, everyone converges on R itself. After it, everyone moves back onto the bucket together. The cache is never fragmented; it just briefly rallies around a different shared value.

Where the PAP fits

This is the gap flagged back in roles.hpp: nothing tied a cached answer to the data version that produced it. Real Zanzibar gets this for free — Spanner assigns every write a TrueTime timestamp, so a revision is a fact about the database, not an assertion by a caller.

revision() is that mechanism in miniature. It is still not a PAP: nothing here persists a write, authorises who may make it, or audits it afterwards. But it is the hook a PAP would drive, and building one no longer requires touching the decision path at all.

How Zanzibar makes a revision trustworthy across machines

The local-clock limitation above is not a detail Google skipped — it is the hardest problem in the design, and they solved it with hardware plus a permanent latency tax. There is no algorithmic shortcut.

TrueTime: make the clock's error explicit

Spanner's TT.now() does not return a timestamp. It returns an interval [earliest, latest] — "the true time is definitely somewhere in here." That interval is kept narrow by GPS receivers and atomic clocks in every datacenter (two sources with uncorrelated failure modes, so one covers the other). The half-width ε is typically under ~4ms, worst case around 7ms.

That is the whole conceptual move: rather than pretend clocks agree, expose exactly how much they might disagree and let the layers above reason about it.

Commit wait: literally wait for time to pass

When a write commits at timestamp s, Spanner does not make it visible immediately. It waits until s is guaranteed to be in the past on every machine — roughly 2ε, call it ~8ms — before releasing the transaction.

It sounds absurd and it is exactly right. Once you have waited out the uncertainty, no later transaction anywhere can commit at an earlier timestamp, even on a machine whose clock runs maximally fast. That buys ordering across independent writers with zero coordination between them — no consensus round, no sequencer, no messages. Just a few milliseconds of patience.

Why only this solves the new enemy problem

The new enemy problem is about real-time ordering: "the revoke happened before this request." It is not about causal ordering, and that distinction is the whole ballgame.

Logical clocks (Lamport, vector clocks) order causally-related events and are cheap. But a revoke by an admin in one datacenter and a read by an attacker in another are causally unrelated — no messages passed between them, nothing to order by. A logical clock reports "concurrent, no defined order", which is precisely the answer that lets a stale Allow through.

Real-time order requires real time. That is why the Zanzibar paper insists on external consistency rather than settling for causal consistency — and why it needed Spanner underneath rather than any ordinary distributed store.

What it costs, and what you do without it

  • ~8ms added to every write, permanently. That is the price tag on the guarantee.
  • Custom hardware in every datacenter. Not something you can install from a package manager.

Without atomic clocks you approximate. CockroachDB uses hybrid logical clocks plus a configured max-offset assumption, giving a weaker guarantee that degrades if NTP drifts past the assumed bound. That is the realistic option for anyone who is not Google — SpiceDB inherits whatever its datastore provides rather than solving this itself.

So the honest position for iam-engine: revision_ = clock_() is the degenerate single-machine case where ε is zero because there is exactly one clock. It is not wrong — it is correct for one writer. The moment there are two, you are choosing between commit-wait-style bounded uncertainty, a coordination round, or a weaker guarantee. There is no free option, and that is the actual lesson.

Build it into iam-engine

The scaffold is committed; three TODOs, and 4 tests currently red:

  1. RoleGraph::addRole — stamp revision_ with clock_().
  2. RoleGraph::assign — the same. Both are writes; miss either one and a cached answer outlives the change that should have killed it.
  3. PolicyEngine::selectSnapshot — apply std::max(chosen, revision) uniformly. The switch currently returns straight out of each case, so restructure it to compute into a local first — otherwise it is far too easy to apply the floor to two levels and quietly forget the third.
ctest --test-dir build -R "SelectSnapshot|AWriteInvalidates" --output-on-failure

The one to watch is RbacCached.AWriteInvalidatesImmediatelyNotAtTheBucketBoundary. Alice is allowed and cached; mid-bucket she is assigned a suspended role that denies. Without the floor she keeps the access she has just lost. That test is lesson 0001's scenario, run against real code, six lessons later.

Worth being sure about before you start: why the floor is max() rather than replacing the chosen snapshot outright. If that is not obvious, ask — it is the difference between preserving sharing and destroying it.
