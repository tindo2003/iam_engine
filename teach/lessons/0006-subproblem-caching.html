Caching the Subproblem

The payoff. Lessons 0001–0004 built a cache for whole checks; lesson 0005 built the roles that finally create something smaller to cache. This one puts them together — and the result is a genuinely different kind of caching than what you have today.

What your cache can and cannot share today

Since written: the whole-check cache was reached through evaluateCached at the time. That function has since been deleted — its key could not capture its own policies argument — and its role is now played by evaluateRbacCached's layer 1, which keys identically. The argument below is unchanged.

The whole-check cache keys on (principal, action, resource, snapshot). Ask yourself what that means for two colleagues: 

alice: db:read on urn:table:users   -> key (alice, db:read, users, S)
bob:   db:read on urn:table:users   -> key (bob,   db:read, users, S)

Two keys. Two full evaluations. And if both are engineers — if the work is literally the same traversal over the same roles — the cache has no way to notice, because the principal is baked into the key.

Now recall the shape you gave evaluateForRole in lesson 0005: 

static Decision evaluateForRole(const RoleGraph&, const RoleName&, const Request&);
//                                                  ^^^^^^^^ no principal

That omission was not an accident, and this lesson is what it was for. "Does engineer allow db:read on urn:table:users?" has one answer, shared by every engineer in the company. Cache that, and alice's check warms the cache for bob — and for everyone hired next year.

Two caches, not one

This does not replace DecisionCache. Real systems run both layers: a whole-check cache that turns a repeat of the exact same request into one lookup, and a subproblem cache underneath that shares work between different requests. The second is what actually scales, because hot roles (employee, an org's base role) get hit by nearly every check in the system.

The key

(role, action, resource, snapshot). Note what changed and what did not: principal is gone, everything else stays — including snapshot, for exactly the reasons lesson 0004 established. A role's policies can be edited, so a per-role answer is snapshot-scoped just like a per-principal one.

That means the whole machinery you already built transfers unchanged: quantize(), selectSnapshot(), eviction, the three consistency levels. You are not designing a new cache — you are reusing the one you have with a different key.

Primary source: How Caching Works in SpiceDB (AuthZed) — the decomposition section describes exactly this, one level deeper (their subproblems nest arbitrarily; yours are one level, which is plenty to see the effect).

Check your understanding

Alice and Bob are both engineers. Alice's check runs first, then Bob's identical-except-for-principal check. What does the subproblem cache add that the whole-check cache cannot?

Why does the subproblem key keep snapshot even though it drops principal?

Build it into iam-engine

Smaller than it sounds — most of the work is already done, and this is mostly about reusing it.

  1. Generalise the cache key. CacheKey is currently {principal, action, resource}. A subproblem key is {role, action, resource} — structurally identical, different meaning. Decide deliberately: rename the field to something neutral (subject?), add a discriminator so a role named "alice" can never collide with a principal named "alice", or use a second cache instance. Each is defensible; the collision question is the one that actually matters.
  2. Add a cached wrapper alongside evaluateForRole, taking a DecisionCache& plus consistency and token, mirroring the whole-check cached path's signature. Reuse selectSnapshot() verbatim.
  3. Watch out: DecisionCache stores bool, but a subproblem answer is a three-valued Decision. Collapsing it to bool reintroduces the exact bug lesson 0005 warned about. You will need to widen what the cache stores — or store two bools, or a small enum. Your call, but do not lose Undecided.
  4. Then prove it actually shares. This is the test that matters, and it is worth writing before the code: give two principals the same role, run a full check for each, and assert the second one did not re-evaluate. cache.size() after both should show one subproblem entry, not two.

Step 3 is the one with a real decision in it — how to store a tri-state in a cache built for bools. Ask before you pick, if the tradeoffs are not obvious; getting it wrong reintroduces a bug you have already fixed once.
