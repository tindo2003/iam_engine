Why You Can't Just Cache an IAM Decision

Ties to MISSION.md's primary goal: understanding IAM evaluation caching. This lesson is the concept you need before any invalidation strategy makes sense.

Your iam-engine project already has a working evaluator — PolicyEngine::evaluate() in src/engine.cpp — that walks every policy's statements on every single call: 

bool PolicyEngine::evaluate(const std::vector<Policy>& policies, const Request& request) {
    bool allowed = false; // default deny
    for (const auto& policy : policies) {
        for (const auto& statement : policy.statements) {
            if (!statement.matchesAction(request.action)) continue;
            if (!statement.matchesResource(request.resource)) continue;
            if (statement.effect == Effect::Deny) return false;
            allowed = true;
        }
    }
    return allowed;
}

That's fine for a handful of statements. It is not fine at the scale real IAM systems run at — Google's Zanzibar paper reports Google's authorization system serving millions of requests per second with p95 latency under 10ms. Re-walking every statement on every request doesn't get you there. The obvious fix: cache the decision.

The naive idea

Keep a map from (principal, action, resource) to the boolean result. First time you see a request, evaluate it the slow way and store the answer. Every repeat of that exact triple after that is an O(1) lookup.

This is a completely reasonable instinct. It is also where almost every real security incident in this space starts.

Where it breaks

Walk through this sequence:

  1. Alice requests db:read on urn:table:users. It's evaluated, allowed, cached.
  2. An admin revokes Alice's access — a Deny statement is added to her policy.
  3. Alice immediately retries the exact same request.

With a naive cache, step 3 returns the cached answer from step 1: Allow. Alice just read data she should no longer be able to touch, and nothing in the system is malfunctioning by its own local logic — the cache did exactly what caches do. The bug is that nobody told the cache the world changed.

The New Enemy Problem

This exact failure mode has a name, from the Zanzibar paper: the new enemy problem. If Alice can act on a permission that was already revoked, she is — from the system's point of view — being treated as a trusted principal after she's become "a new enemy." Zanzibar's whole external-consistency design (its "zookie" tokens) exists specifically to make this failure mode impossible, not just unlikely.

Primary source for this lesson: Zanzibar: Google's Consistent, Global Authorization System (USENIX ATC 2019) — read at least the sections on external consistency and "new enemy problem" before the next lesson.

Check your understanding

An admin revokes Bob's access. Bob immediately retries a request that was cached as Allow 3 seconds ago, under a plain 60-second TTL cache with no other invalidation. What happens?

Try it on the real codebase

Don't build the fix yet — that's lesson 0002, once you've read the primary source above. But go look at your own project with this lesson's lens:

  • Open tests/test_engine.cpp and find test_deny_from_a_different_policy_still_wins. Notice that every test evaluates fresh — nothing is cached yet, so the new enemy problem doesn't exist in your engine today. It will the moment you add a cache, if you're not deliberate about invalidation.
  • Think concretely: if you added a std::unordered_map<RequestKey, bool> cache in front of PolicyEngine::evaluate right now, what's the smallest change to Policy or PolicyEngine that would let you correctly invalidate it the instant a policy changes — without scanning every cache entry one by one?

Sit with that question. Lesson 0002 covers the three real answers (TTL, version-stamped, event-driven) and you'll build a DecisionCache class into iam-engine that has a test proving it — the same way test_engine.cpp proves deny-overrides-allow today.
