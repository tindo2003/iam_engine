How SpiceDB Actually Caches (Quantized Time Beats Fancy Invalidation)

Follows Lesson 0001. That lesson ended by asking: what's the smallest change that invalidates a cache the instant a policy changes? The real answer, from a production Zanzibar implementation, is more pragmatic than the question assumed.

Correcting lesson 0001

Lesson 0001 framed the goal as "make staleness detectable and boundable, not just time-boxed by a TTL" — implying TTL was the lazy answer. SpiceDB, a real open-source Zanzibar implementation, says otherwise: its default hotspot cache is a flat 5-second TTL. From their own writeup — staleness up to that window is "perfectly acceptable" for most checks, because the rare case (an ACL changing inside that exact window) has a small, bounded blast radius.

The nuance isn't "TTL vs. something smarter." It's: use a cheap TTL for the common case, and give callers an explicit way to demand freshness for the specific checks that need it. That second half is what lesson 0001 was missing.

What actually gets cached

SpiceDB doesn't cache whole top-level checks. It decomposes a check like document:doc1#view@user:jill into smaller subproblems — e.g. document:doc1#reader@user:jill, org:acme#can_admin@user:jill — and caches those. Two different top-level checks that happen to share a subproblem both benefit from one cache entry, which a whole-check cache would miss entirely.

The cache key includes a quantized timestamp

Every cache key carries a snapshot timestamp, not just (subject, action, resource). Under the default minimize_latency consistency level, that timestamp is quantized — rounded into fixed buckets (e.g. 1-second windows) — so many real requests inside the same window collide onto the identical key. Without quantization, "the current time" is different on every request and the cache would never hit at all.

The escape hatch: consistency is a per-request choice

minimize_latency (default)
Quantized timestamp, maximum cache reuse, bounded staleness. What almost every check should use.
fully_consistent
A unique timestamp every time — effectively disables caching for that request. Use for the one check that truly can't tolerate staleness (e.g. an admin confirming their own revoke just took effect).
at_least_as_fresh
Carries a ZedToken (SpiceDB's zookie from lesson 0001) — guarantees a snapshot at least that recent, while still allowing cache hits for anything at or after it. This is external consistency, shipped as an actual API parameter.

Why one cache per server isn't enough

If every server in a cluster caches independently, a cluster of N servers with M bytes each can still only cache M/B unique subproblems total — no better than one machine, just duplicated. SpiceDB routes each subproblem to the same node via consistent hashing (a "token hashring"), so the cluster's real capacity becomes N×M/B. Same idea as the Leopard indexing mentioned in the caching glossary, applied to cache placement instead of statement lookup.

Build it into iam-engine

Rescoped from lesson 0001's guess. Here's the concrete, testable version to build in your own iam-engine checkout:

  1. Add a DecisionCache class: key = (principal, action, resource), value = {bool decision; std::chrono::steady_clock::time_point cachedAt;}.
  2. Inject the clock (a std::function<std::chrono::steady_clock::time_point()> defaulting to std::chrono::steady_clock::now) so tests can fake time passing without a real sleep() — same constructor-injection pattern you'd want for anything time-dependent.
  3. get() is a hit only if now - cachedAt < ttl; otherwise treat it as a miss and let the caller re-evaluate and put() a fresh entry.
  4. Add one bypass path — a evaluate(..., Consistency::FullyConsistent) overload or flag — that skips the cache unconditionally, mirroring fully_consistent above.
  5. Write tests/test_cache.cpp with three cases: (a) a repeat request inside the TTL is a cache hit (evaluate the underlying policies only once — you can assert this with a call counter); (b) advancing the fake clock past the TTL makes the same request a miss and re-evaluates; (c) the fully-consistent path never hits the cache regardless of TTL.

Build it, then tell me what broke or what didn't fit the plan — that's more useful to work through than getting it right on the first try. Ask me anything that's unclear before you start, too.
