Thread Safety Is Not Deduplication

Two separate problems that get conflated constantly. Fixing the first leaves the second completely untouched — and the second is the one that actually costs you at scale.

Where this started

Back in lesson 0004 you asked what happens when ten identical requests fire at once, and whether quantization prevented the redundant work. The answer at the time — recorded in learning record 0001 — was no: quantization makes concurrent writes agree, it does not stop them happening. This lesson is the follow-through.

It also had a prerequisite that was quietly broken the entire time. DecisionCache::entries_ and RoleGraph's maps were plain unordered_maps with no locking at all. Using them from two threads was not "slightly stale" — it was a data race, which is undefined behaviour. Not a wrong answer: no answer, no guarantees, anything at all.

Problem one: the containers

Both classes now hold a std::shared_mutex, not a plain one. That choice follows from the access pattern being lopsided: every check reads; only administration writes. A plain mutex would make readers queue behind each other for no reason. A shared mutex lets any number of readers proceed together and only excludes them for a write. 

RoleGraph::addRole / assign        unique_lock   (writes)
RoleGraph::find / effectiveRoles / revision
                                   shared_lock   (reads)
One lock for the whole traversal, not one per node

effectiveRoles takes a single shared_lock and holds it across the entire breadth-first walk. That is why findUnlocked and effectiveRolesUnlocked exist — the public methods lock and delegate, the traversal uses the unlocked variants.

Locking per node lookup instead would let a write land between two steps of the walk, producing a role set that mixes pre- and post-write state — a set the graph never actually held at any instant. That is precisely the bug demos/snapshot_consistency_race.cpp reproduces. When you built that demo it was illustrative, describing a problem evaluate() could not have. It is now the thing this lock is defending against.

Problem two: the work

Here is the part that surprises people. Suppose ten threads ask for the same uncached key at the same instant, and the cache is fully thread-safe. What happens?

All ten miss. All ten run the full evaluation. All ten store the identical answer. Nothing is corrupted, no invariant breaks, every caller gets the right result — and you did ten times the work. The mutex protects the container; it has nothing to say about the computation.

That is the thundering herd, and it is worst exactly where it hurts most: a hot key that just expired, with every request in flight racing to recompute it.

Singleflight

DecisionCache::getOrCompute fixes it. The first caller for a key registers an in-flight entry and computes; everyone arriving while that is running waits on its result instead of starting their own. 

fast path        cached? return it
register         take exclusive lock
                 re-check the cache
                 either join an existing flight, or become its owner
owner            compute WITHOUT the lock, store, fulfil, retire
joiner           wait on the shared_future

Three details that are not decoration

  • Compute runs with no lock held. A policy evaluation is the slow part; holding the mutex across it would block every unrelated reader in the process on work they have no interest in.
  • The registration step takes an exclusive lock even though it begins by reading. It re-checks the cache under that lock, because another thread may have finished between the fast path and here. Doing the check under a shared lock would let two threads both conclude "nobody is computing this" and both register a flight — reintroducing the duplication this exists to remove.
  • A throwing compute retires its flight before rethrowing. Otherwise every waiter blocks forever on a promise nobody will ever fulfil. An exception in one thread would hang all the others.

Check your understanding

Ten threads request the same uncached key simultaneously, against a cache that is thread-safe but has no singleflight. What happens?

Why does getOrCompute take an exclusive lock to register a flight, when it starts by reading?

Why does effectiveRoles hold one lock across the whole traversal rather than locking each node lookup?

Verify it yourself

Passing tests are weak evidence for concurrency work — a race can hide for a thousand runs. Build under ThreadSanitizer instead: 

cmake -S . -B build-tsan -DCMAKE_BUILD_TYPE=Debug \
      -DCMAKE_CXX_FLAGS="-fsanitize=thread -g" \
      -DCMAKE_EXE_LINKER_FLAGS="-fsanitize=thread"
cmake --build build-tsan
./build-tsan/tests/test_cache
Validate the tool before trusting its silence

A sanitizer that silently failed to instrument reports zero races. So does a genuinely clean program. They look identical.

Before believing a clean TSan run, compile a deliberately racy program with the same flags and confirm it is reported. Two unsynchronised threads incrementing a global is enough. That takes a minute and converts "no output" from ambiguous into meaningful.

This is the same discipline as writing a test that fails before you fix the bug. Evidence of absence is only evidence if the detector works.

What this does not solve

Singleflight deduplicates within one process. Ten processes behind a load balancer still compute the same key ten times, because neither the cache nor the in-flight map is shared between them. That is the consistent-hashing problem parked in NOTES.md — route a key to the same node every time and the deduplication becomes cluster-wide.

Same shape as every other limit in this project: the mechanism is right, its authority is local.
