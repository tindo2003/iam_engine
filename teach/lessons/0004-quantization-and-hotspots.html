Quantization and the Hotspot Problem

Lessons 0001–0003 built a cache for one request at a time: TTL, then a version floor. This lesson is about what happens when the same request arrives thousands of times a second — the case the Zanzibar paper calls "the most critical frontier in our pursuit of low latency and high availability."

The hotspot problem

A hotspot is authorization data checked far more often than the rest — a viral post, a popular shared doc, an org's root folder. Your current DecisionCache handles this fine on a single process: the second identical request is a cache hit. The problem only shows up once you have more than one server.

If each server in a cluster caches independently, a cluster of N servers with M bytes of cache each doesn't get you N×M bytes of useful caching — it gets you the same effective M/B unique problems as a single machine, just duplicated N times, because nothing guarantees two near-simultaneous identical requests land on the same server. Worse: even on one server, if two requests for the exact same thing arrive 50ms apart, the first one hasn't finished computing and caching its answer yet when the second one arrives — so without something forcing them together, both pay the full evaluation cost.

Fix 1: quantization (this lesson's build)

SpiceDB's default minimize_latency level doesn't stamp a cache entry with the exact instant it was computed. It rounds that timestamp down to a fixed window — e.g. the start of the current 1-second bucket — before using it. Two requests 50ms apart, or 900ms apart, both round down to the same bucket boundary, so they naturally collapse onto the same effective freshness window instead of each starting its own independent TTL countdown from its own instant.

This is a small change with an outsized effect: it's the difference between "N requests in a burst individually decide whether they're still fresh" and "N requests in a burst share one answer to that question."

Fix 2: consistent hashing (conceptual only — not built here)

Quantization alone doesn't fix the multi-server duplication problem — two different servers can each independently reach the right conclusion and still both do the work. SpiceDB's answer is a token hashring: consistent hashing routes the same problem to the same server(s) every time, so a cluster of N servers caches N×M/B unique items instead of just M/B. This only matters once there's more than one process, which is out of scope for a single-process `iam-engine` — worth understanding why it exists, not worth building here.

Primary source for this lesson: Hotspot Caching in Google Zanzibar and SpiceDB (AuthZed).

Check your understanding

In a cluster of N servers, each caching independently with no coordination, why does a hotspot item NOT get N times the effective caching benefit?

What does rounding a cache entry's timestamp down to a fixed bucket actually buy you?

Build it into iam-engine

Scoped steps, no full skeleton this time — you've done this shape twice already:

  1. Add a quantization window (e.g. std::chrono::milliseconds bucketSize) to DecisionCache, alongside ttl_.
  2. Write a private helper that rounds a time_point down to the start of its bucket — integer division on the duration since some fixed epoch is the usual trick: floor(t / bucketSize) * bucketSize.
  3. In put(), stamp cachedAt with the quantized value of clock_(), not the raw instant.
  4. The test that proves it matters: two separate put() calls for the same key, at two different (fake-clock) instants that fall inside the same bucket, should produce entries with an identical cachedAt — and therefore an identical TTL expiry boundary — even though the real instants differed. A third call just past the bucket boundary should get a different, later cachedAt.

If the bucket-rounding math itself (the floor-division trick) isn't clicking, ask before you start — it's a five-minute concept once it clicks and a frustrating one to debug from first principles.
